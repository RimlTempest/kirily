# ADR-0027: 回転は「見え方」であって「画像」ではない

- 状態: 採用
- 日付: 2026-09-22

## 背景

要望は「画像の回転」だったが、理由は**スマホで手作業の消し込みがしづらい**
ことだった。

横長の写真を縦長の画面に収めると、**幅で決まる**。Pixel 7（412×839）に
1600×600 を入れると **24%**。1 画素が 0.24 画素で表示されている状態で
髪の隙間を塗れ、というのは無理がある。

90° 回せば**高さで決まる**ようになる。同じ画像が **35%** になる。1.46 倍。

## 決定

**ビューポートの性質として持つ。** ズームやパンと同じ側に置く。

```ts
export type Viewport = {
  readonly scale: number
  readonly offsetX: number
  readonly offsetY: number
  readonly rotation: Quarter // 0 | 90 | 180 | 270
}
```

**マスクも、トリミングも、書き出しも回転を見ない。** 元画像のバッファは
最初から最後まで同じ向きのままで、`Quarter` は画面座標から画像座標へ
変換する経路にしか現れない。

### なぜ画像そのものを回さないのか

回すと「元画像を書き換えない」（CLAUDE.md）に触れる。32MB のバッファを
もう一枚確保して詰め替えることになり、しかも**回転のたびに**起きる。

さらに、マスクは元画像と同じ解像度で持っている（`kirily-image-pipeline` §3）。
画像を回せばマスク 3 層も回すことになり、`affectedRect` に基づく履歴が
全部無効になる。90° 回しただけで Undo が効かなくなる。

得られるものは「書き出しの向きが変わる」ことだけで、**それは要望ではなかった。**

### 原点まわりに回す

回転の中心を画像の中心にすると、`fitViewport` と `centred` に「画像の大きさ」
という引数がもう一つ要る。原点まわりなら、大きさに依存する平行移動は
`offsetX` / `offsetY` に畳み込める。変換は 2 引数のまま。

```ts
const turn = (x: number, y: number, rotation: Quarter) => {
  if (rotation === 90) return { x: -y, y: x }
  if (rotation === 180) return { x: -x, y: -y }
  if (rotation === 270) return { x: y, y: -x }
  return { x, y }
}
```

戻す側は逆回しを引くだけにした。`(360 - rotation) % 360` は数としては
正しいが、`Quarter` に戻すのに型アサーションが要る（`kirily/no-type-assertion`
が落とす）。4 つしか無いのだから全部書けば良い。

```ts
const OPPOSITE: Record<Quarter, Quarter> = { 0: 0, 90: 270, 180: 180, 270: 90 }
```

### 「全体」は向きを変えない

`fit()` は現在の `rotation` を保ったまま収め直す。収めるのは**枠**の話で、
どちらを上にして見ているかとは別の話だから。

## 測ったこと

| 画像     | 画面    | そのまま | 90° 回して |
| -------- | ------- | -------- | ---------- |
| 1600×600 | 412×839 | 24%      | **35%**    |
| 120×120  | 412×839 | 100%     | 100%       |

下の行が重要で、**テストの前提を 2 回間違えた。** `fitViewport` は 100% を
超えて拡大しない（ADR より前からの仕様）。だから**既に収まっている画像は
回しても何も起きない。** 単体テストでも E2E でも正方形のフィクスチャを
使っていて、どちらも「効果が無い」ことを「効果がある」として書いていた。
1200×400 を生成する経路をテストに足して直した。

書き出しは向きに依らず同じ:

```
そのまま 120×120 → 回して 120×120
```

## モバイルで一度壊した

ズーム行が横に収まらず、**あふれて切れたのが回転ボタンだった。**
この機能が存在する唯一の端末で、押せなかった。

最初の直しはズームのプリセットを隠すことだったが、それは**機能を減らす
直し方**で、モバイルのテストに落とされた。`flex-wrap` + `max-w-full` にして
2 行に折り返す。角丸は `rounded-full` から `rounded-2xl` に —
2 行入った丸薬は丸薬ではない。

## テスト

単体 8 件、E2E 7 件（回転そのものに 5 件、レンダラ等価性に 2 件）。

レンダラ等価性に `turned a quarter` と `turned three quarters` を足した。
**回転を戻す処理は 2 か所に、2 つの言語で書いてある**（WebGL2 の
フラグメントシェーダと `viewport.ts`）。片方だけ 90° ずれていても、
片方だけ見ていては誰も気付かない。

回転そのものの 5 件:

- 90° ずつ巡回して、いまどこかをボタンが言う
- **横長の画像が縦長の画面で大きくなる**（この機能が存在する理由）
- 回した状態でも**ポインタの真下に塗れる**（座標系を混ぜていない）
- **書き出したファイルの寸法が向きで変わらない**
- 回した状態でも**ファイルの正しい画素に塗れている**（背景透過の後）

## 却下した案

**任意角度。** 画素の再標本化が要る。見るためだけに元画像の情報を
落とすのは、Kirily がやらないと決めたことそのもの。

**書き出しにも回転を効かせる切り替え。** 要望ではなかったし、
入れた瞬間に「いま書き出したら縦か横か」を画面のどこかが
常に答えていなければならなくなる。
