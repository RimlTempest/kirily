# ADR-0017: シャードを一度に取りに行く

- 状態: 採用
- 日付: 2026-09-21

## 背景

ADR-0015 の計測で、高精度段の初回は `ai_load` 2475ms が支配していた。
ただしこれは 1 つの数字で、ダウンロード・検証・コンパイルが潰れている。
ADR-0015 が `ai_load` と `ai_inference` を分けたのと同じ理由で、
もう一段割った。

| 段           | 実測              |
| ------------ | ----------------- |
| `ai_fetch`   | **2043ms（83%）** |
| `ai_compile` | 377ms             |
| `ai_verify`  | 53ms              |

**しかもこれは localhost の数字である。**

原因は `for (const shard of shards) await ...` だった。
84 MiB を 24 MiB のシャード 4 つに分けておきながら、
1 つずつ順番に待っていた。

## 決定

**シャードの大きさをマニフェストに書き、全部同時に取りに行く。**

順番が問題なのではなく、**順番に依存していること**が問題だった。
各シャードの大きさが先に分かっていれば、それぞれ自分の置き場所が分かるので、
返ってくる順番は関係なくなる。

```json
{
  "shards": ["m.000", "m.001", "m.002", "m.003"],
  "shardBytes": [25165824, 25165824, 25165824, 12654236]
}
```

### マニフェストの自己矛盾は読む前に落とす

`shardBytes` の個数が `shards` と合わない、あるいは合計が `bytes` と違う
マニフェストは `isWeightManifest` で弾く。
**オフセットがずれたモデルはエラーにならない。** それらしい、
しかし間違ったマスクを出すだけである（`kirily-image-pipeline` の規約）。

### ボディはストリームで置き場所へ直接書く

`response.arrayBuffer()` で受けると、24 MiB のバッファが 4 つ同時に
生きることになり、スマートフォンでのピークが倍になる。
`body.getReader()` で 64KB ずつ、最終的に渡すバッファへ直接書けば、
**全部同時に取りに行っても余分な確保はほぼ無い**。
進捗がバイト単位で正確になるのもついでに手に入る。

シャードが宣言より短くても長くても、そこで落とす。
残りのシャードが間違ったオフセットに載るからである。

## 測った結果

`pale-subject-on-white.png`、IS-Net fp16（84 MiB）、localhost、2 回連続。

|            | 前     | 後                |
| ---------- | ------ | ----------------- |
| `ai_fetch` | 2043ms | **715 / 718ms**   |
| `ai_load`  | 2475ms | **1158 / 1158ms** |

ダウンロードが **65% 短縮**、`ai_load` 全体で **53% 短縮**。

localhost で消えたのはほぼリクエストごとのオーバーヘッドなので、
実ネットワークでは並列の TCP ストリームぶんだけさらに効く。

## 残っているもの

`ai_load` 1158ms の内訳は `ai_fetch` 715 + `ai_compile` 390 + `ai_verify` 50。

- **`ai_compile` 390ms** — ORT がセッションを組む時間。こちらから触れる部分が少ない
- **`ai_verify` 50ms** — 84 MiB の SHA-256。取得中に逐次計算すれば隠せるが、50ms に見合わない
- **`ai_fetch` 715ms** — 84 MiB / 0.715s ≒ 118 MB/s で、ループバックの限界に近い

次の手は**キャッシュ**である。2 回目の訪問でも 715ms を払っている。
ただし `/models/<id>/<file>` はモデルを差し替えても名前が変わらないので、
`immutable` を付けると古い重みを配り続ける。
SHA-256 検証があるので**壊れたことは分かる**が、動かなくなる。
安全にやるならパスにハッシュを入れる必要があり、それは別の変更になる。

## 却下した案

**全部 `arrayBuffer()` で受けてから連結する。** マニフェストを変えずに済むが、
ピークが 84 MiB から 168 MiB になる。4K の画像を開いている最中に起きることなので、
払えない。

**同時実行数を絞る。** ストリームで直接書いている以上、
絞って守るものが無い。
