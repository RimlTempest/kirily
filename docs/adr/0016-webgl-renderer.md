# ADR-0016: 合成を GPU に渡す

- 状態: 採用
- 日付: 2026-09-21

## 背景

ADR-0015 の計測が名指ししたのはレンダラだった。

| キャンバス                 | 1 フレーム | fps    |
| -------------------------- | ---------- | ------ |
| 800×600                    | 12.1ms     | 83     |
| 1440×900                   | 26.9ms     | 37     |
| 2560×1600（Retina 全画面） | 84.6ms     | **12** |

`renderViewport` はキャンバスの画素を 1 つずつ JavaScript で回り、
色を読み、マスクを読み、縁が柔らかければ合成の式を解く。画素あたり約 20ns。

**これはフラグメントシェーダそのものである。** 名前が違うだけで、
GPU がまさにこの形のために作られている。

## 決定

**WebGL2 のフラグメントシェーダに移し、Canvas 2D の経路は残す。**

段階的な劣化は既定の方針で、レンダラは機能単位で落ちる
（`kirily-image-pipeline` §9）。`createWebglRenderer` は WebGL2 が無い、
あるいはプログラムがリンクできないときに `null` を返す。呼び手は落ちずに切り替える。

### 一度だけ決める

キャンバスは**一生に 1 種類のコンテキストしか渡さない**。`webgl2` を
取ったあとに `2d` を頼むと `null` が返る。「GPU で試して駄目なら後で戻る」は
この API では成立しない。だから最初のフレームの前に決める —
`createWebglRenderer` が可否を答えるのもそこである。

### アップロードは変わったものだけ

マスクは筆を 1 本引くたびに変わる（1254² で 1.5MB）。
色は開いたとき 1 回、背景フィールドは AI が走ったとき 1 回。
パンしただけのフレームで再アップロードすると、削ったコストがそのまま戻る。
`maskVersion` を見て判断する。

### `premultipliedAlpha: false`

キャンバスは市松模様の上に重ねられ、テストから読み戻される。
どちらも**ストレートアルファ**を期待している。
`putImageData` が書いていたものと同じである。

### 同じ絵でなければならない

近い絵ではなく、同じ絵である。違えば、利用者が見ているものと
書き出されるものが食い違う。Preview / Export を分けた理由そのものが崩れる
（kirily-design.md §16）。

`tests/e2e/specs/renderer.spec.ts` が同じファイルを両方の経路に通し、
**全画素・全チャンネルを比較する**。2 回のページ読み込みで比較するのは、
1 つのキャンバスが 2 つのコンテキストを持てないからである。

- フィット表示（双方バイリニア）
- 150% 超（双方ニアレスト。GPU 側はサンプラー、CPU 側は分岐で、
  ここは静かに食い違いやすい）

結果は**最大差 2 / 255、2 を超える画素は 0、平均差 0.5 未満**。
バイト単位で一致させていないのは設計上の判断で、CPU 側は
バイリニアの結果を毎回バイトに丸めてから合成し、GPU 側は書き出しまで float のまま持つ。
1 段ずれることはあるが、間違った絵がこの幅に隠れることはない。

## 測った結果

1600×1000 のウィンドウ、キャンバス 892×868（0.77M px）、
`pale-subject-on-white.png`、パン 60 回。

|           | メインスレッド       | 60 回の実時間 |
| --------- | -------------------- | ------------- |
| Canvas 2D | **55.78ms/フレーム** | 3998ms        |
| WebGL     | **0.02ms/フレーム**  | 1008ms        |

**0.02ms は GPU の待ち時間を含まない。** `drawArrays` は非同期で、
直後の `performance.now()` は投入が終わった時刻を返す。

含まないことが問題ではなく、**これこそが知りたい数字である**。
ブラシの反応を決めるのはメインスレッドが入力を受けられるかどうかで、
そこが 55.78ms から 0.02ms になった。

実時間の 1008ms は測定側の入力レート（CDP の往復で 1 回 17ms 程度）に
律速されているので、WebGL の真の 1 フレームはそれより短い。
Canvas 2D の 3998ms は律速されておらず、1 回 66ms かかっている。

## 副作用

E2E のヘルパーがエディタのキャンバスに `getContext('2d')` を呼んでいて、
WebGL キャンバスでは `null` が返るため 8 件落ちた。
`createImageBitmap` 経由で読むように `canvas.ts` へ集約した。
どちらのコンテキストでも動く。

## 却下した案

**WebGPU で書く。** レンダラの要求はテクスチャを 3 枚読んで四角形を 1 枚描くことで、
WebGL2 で足りる。WebGPU は対応端末が狭く、
`ort-session.ts` が既に WebGPU を使っているので、
レンダラまで同じアダプタを奪い合わせる理由が無い。

**Canvas 2D の経路を消す。** WebGL2 が無い環境はまだある。
落ちる理由にはしない。

**CPU 側を最適化する。** 型付き配列の書き方を詰めれば 2 倍にはなるだろうが、
ここで必要なのは 2 倍ではなく 2 桁である。
